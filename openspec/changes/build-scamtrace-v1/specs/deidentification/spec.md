# Spec Delta

## Purpose

在對話寫入資料庫或送出本機之前，偵測並以一致代號取代個人識別資料，同時保留金額與網域等判斷詐騙所需的線索。

## ADDED Requirements

### Requirement: 個資類型與代號
系統 SHALL 偵測下列個資並換成代號：信用卡號 `[卡號N]`、身分證字號 `[身分證N]`、居留證號 `[居留證N]`、Email `[信箱N]`、手機（含 `09-XXXX-XXXX` 寫法與中國大陸手機）與市話 `[電話N]`、銀行帳號 `[帳號N]`、LINE ID `[LINEIDN]`、地址 `[地址N]`、「護照」字樣後的護照號碼 `[護照N]`。N 為同類型中依首次出現順序的編號。

#### Scenario: 手機號碼
- **WHEN** 訊息內容為「打給我 0912-345-678」
- **THEN** 遮罩後為「打給我 [電話1]」

#### Scenario: 表單式個資
- **WHEN** 訊息內容為多行表單，含「電話號碼：0912345678」「身分證字號：A123456789」「護照號碼：312345678」「Email:fake@example.com」與地址
- **THEN** 每一項個資都被換成對應代號，原值不出現在遮罩後文字中

#### Scenario: 身分證字號
- **WHEN** 訊息內容含 `A123456789`
- **THEN** 該字串換成 `[身分證1]`

#### Scenario: 居留證號
- **WHEN** 訊息內容含 `AC12345678`
- **THEN** 該字串換成 `[居留證1]`

#### Scenario: 地址
- **WHEN** 訊息內容含「台北市大安區復興南路一段100號」
- **THEN** 該地址換成 `[地址1]`

#### Scenario: LINE ID
- **WHEN** 訊息內容為「加我 abc_123」
- **THEN** 英數字串換成 `[LINEID1]`

### Requirement: 信用卡號需通過檢查碼
13–19 位數字（可含空白或 -）只有在通過 Luhn 檢查碼時 SHALL 視為信用卡號；未通過者 MUST 交由後續規則判斷。

#### Scenario: 合法卡號
- **WHEN** 訊息內容含 `4111 1111 1111 1111`
- **THEN** 換成 `[卡號1]`

#### Scenario: 未通過 Luhn 的 16 位數字
- **WHEN** 訊息內容含未通過 Luhn 的 16 位連續數字
- **THEN** 不被當成卡號，而是由銀行帳號規則換成 `[帳號N]`

### Requirement: 比對順序避免誤判
規則 SHALL 依「卡號 → 身分證 → 居留證 → Email → 網址 → 手機 → 市話 → 銀行帳號 → LINE ID → 地址 → 發話者名字」的順序套用，已被替換的文字 MUST NOT 再被後續規則比對。數字類規則 MUST 以前後非數字為邊界，不得只比對一長串數字的一部分。

#### Scenario: 帳號不被拆成電話
- **WHEN** 訊息內容含 14 位數字帳號 `09123456789012`
- **THEN** 整串換成單一 `[帳號1]`，不會出現 `[電話1]` 加上剩餘數字

### Requirement: 同值同代號
同一個原值在整段對話中 MUST 使用同一個代號，不同原值 MUST 使用不同代號。

#### Scenario: 同一帳號出現三次
- **WHEN** 帳號 `12345678901234` 在第 3、8、15 則訊息各出現一次
- **THEN** 三處都換成 `[帳號1]`

#### Scenario: 兩個不同電話
- **WHEN** 對話中出現 `0912345678` 與 `0987654321`
- **THEN** 分別換成 `[電話1]` 與 `[電話2]`

### Requirement: 保留網域與金額
網址 SHALL 保留協定與網域，只把路徑與參數換成 `[路徑]`；金額（例如「先匯 3 萬」「NT$30,000」）MUST NOT 被遮罩。

#### Scenario: 網址遮罩
- **WHEN** 訊息內容含 `https://example.com/login?id=abc`
- **THEN** 遮罩後為 `https://example.com/[路徑]`

#### Scenario: 金額保留
- **WHEN** 訊息內容為「先匯 3 萬，明天再補 NT$30,000」
- **THEN** 遮罩後內容不變

### Requirement: 發話者匿名化
使用者指定為自己的發話者 SHALL 換成「我」，其他發話者依首次出現順序換成「對方A」「對方B」…；這些名字在訊息內文中出現時也 MUST 一併替換。

#### Scenario: 內文出現對方名字
- **WHEN** 發話者「王小明」被指定為對方，且某則訊息內容為「我是王小明啦」
- **THEN** 該則發話者顯示為「對方A」，內容變為「我是對方A啦」

### Requirement: 去識別化統計
系統 SHALL 計算每種個資類型被遮罩的處數，供預覽頁顯示並隨案例保存；統計 MUST NOT 包含原值。

#### Scenario: 統計數量
- **WHEN** 對話中有 2 個不同電話共出現 3 次、1 個帳號出現 2 次
- **THEN** 統計顯示 phone 3、bank_account 2

### Requirement: 手動補遮
預覽階段使用者 SHALL 能選取遮罩後文字中的任意片段並遮罩；該片段在整段對話中的所有出現處 MUST 一併換成同一個代號，並更新統計。

#### Scenario: 遮罩第三人姓名
- **WHEN** 使用者在預覽頁選取「林大華」並按「遮罩」
- **THEN** 全文所有「林大華」換成同一個代號（例如 `[遮罩1]`），統計中 manual 類型數量增加

### Requirement: 原值不外流
原文與「代號 ↔ 原值」對照表 MUST NOT 寫入資料庫、日誌或任何暫存檔，也 MUST NOT 送往語言模型；暫存與後續處理只使用遮罩後文字。

#### Scenario: 暫存檔不含原值
- **WHEN** 使用者上傳含電話 `0912345678` 的對話並進入預覽
- **THEN** 伺服器暫存檔、資料庫與送往語言模型的內容都找不到 `0912345678`
